== Preview Features

=== Value Classes (JEP 401)

xref:storage:value-classes.adoc[Value Classes] are a preview feature of the JDK, so an application using them needs additional VM parameters.
None of them is required for an application that does not use value classes.

[options="header",cols="2,3"]
|===
| VM parameter | Why it is needed

| `--enable-preview`
| Required by the JDK for any preview feature. Without it, value classes do not exist at runtime and nothing about them applies.

| `--add-exports java.base/jdk.internal.misc=ALL-UNNAMED`
| `sun.misc.Unsafe` refuses the field offsets of fields declared inside a value class, exactly as it already does for records. Alternatively, put the `eclipse-serializer-nativememory` module on the classpath: it registers a JNI-based memory accessor through `ServiceLoader` and needs no flags at all.

| `--enable-final-field-mutation=ALL-UNNAMED`
| Only on a JDK that blocks final field mutation. Putting a value object into its owner writes the owner's field, which may be `final`.
|===

[NOTE]
====
The last two parameters name the module performing the access, which is {product-name}'s rather than the application's.
`ALL-UNNAMED` covers it on the class path; a module path deployment names `org.eclipse.serializer.persistence.binary`.
====

== Third Party Libraries

{product-name}'s core itself doesn't have any dependencies to other libraries whatsoever.
So you don't have to worry about potential conflicts in your environment.
This was a matter of choice of ours to keep the life of the developers using {product-name} as simple as possible.
On the other hand feel free to include any dependencies you need, {product-name} will play along well, e.g.
a logging framework of your choice.
