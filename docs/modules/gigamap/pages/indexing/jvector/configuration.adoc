= JVector Configuration

The `VectorIndexConfiguration` builder provides various options to tune the index for your specific use case.

[#jvm-configuration]
== JVM Configuration

To enable SIMD acceleration via the Panama Vector API, configure your JVM with the following parameters.

=== Required JVM Arguments

[source, bash]
----
java --add-modules jdk.incubator.vector -jar your-app.jar
----

=== Full Example with Performance Tuning

[source, bash]
----
java --add-modules jdk.incubator.vector \
     -Djvector.physical_core_count=8 \
     -jar your-app.jar
----

=== Maven Configuration

For Maven projects, configure the Surefire and Failsafe plugins:

[source, xml]
----
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <configuration>
        <argLine>--add-modules jdk.incubator.vector</argLine>
    </configuration>
</plugin>
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-failsafe-plugin</artifactId>
    <configuration>
        <argLine>--add-modules jdk.incubator.vector</argLine>
    </configuration>
</plugin>
----

=== Gradle Configuration

For Gradle projects:

[source, kotlin]
----
tasks.withType<JavaExec> {
    jvmArgs("--add-modules", "jdk.incubator.vector")
}

tasks.withType<Test> {
    jvmArgs("--add-modules", "jdk.incubator.vector")
}
----

=== Physical Core Configuration

Intensive SIMD operations can saturate memory bandwidth during indexing and PQ computation. JVector mitigates this by using a `PhysicalCoreExecutor` that limits concurrency to physical cores rather than logical cores (hyperthreads).

[options="header",cols="1,1,3"]
|===
|Property |Default |Description

|`jvector.physical_core_count`
|Half of available processors
|Override the detected physical core count for parallel operations
|===

NOTE: The `jdk.incubator.vector` module is an incubator feature in Java 17-21. Starting with Java 22, the Vector API moved to preview status. JVector's multi-release JAR handles the API differences automatically, but the module must still be explicitly enabled.

== Basic HNSW Parameters

[options="header",cols="1,1,3"]
|===
|Parameter |Default |Description

|`dimension`
|(required)
|Vector dimensionality. Must match the size of your embedding vectors.

|`similarityFunction`
|`COSINE`
|Similarity metric (`COSINE`, `DOT_PRODUCT`, `EUCLIDEAN`).

|`maxDegree`
|16
|Maximum connections per node in HNSW graph. Higher values improve recall but increase memory usage. With `approximateScoring=FUSED_PQ`, this also multiplies the per-node fused block (`pqSubspaces * maxDegree` bytes), so it drives both the graph size and the bytes read per traversal hop.

|`beamWidth`
|100
|Beam width during index construction (HNSW _efConstruction_). Higher values improve graph quality but slow down construction. Has no effect at query time.

|`minSearchBeamWidth`
|100
|Minimum beam width during search (HNSW _efSearch_ floor). The effective beam width is `max(k, minSearchBeamWidth)`. Keeps the top-k stable across different `k` values; set to `1` to disable the floor and make the beam width equal to the requested `k`. Independent of `beamWidth`. Can be overridden per query via `search(query, k, searchBeamWidth)`.

|`neighborOverflow`
|1.2
|How many candidate neighbours construction keeps before pruning, as a multiple of `maxDegree`. Higher values select neighbours slightly better at the cost of more memory while building. Minimal effect on final quality or query speed - the default suits almost everything.

|`alpha`
|1.2
|Aggressiveness of the RNG pruning heuristic during construction. `1.0` keeps every Voronoi neighbour; higher values drop edges reachable by other paths, giving a sparser graph and faster queries at the cost of some recall. Raise it only under memory pressure.
|===

=== Example

[source, java]
----
VectorIndexConfiguration config = VectorIndexConfiguration.builder()
    .dimension(768)
    .similarityFunction(VectorSimilarityFunction.COSINE)
    .maxDegree(32)
    .beamWidth(200)
    .build();
----

== On-Disk Storage

For datasets that exceed available memory, enable on-disk storage to use memory-mapped files. See xref:indexing/jvector/advanced.adoc#_on_disk_index_with_compression[On-Disk Index with Compression] for an in-depth explanation of the build/persist lifecycle, memory-mapped access, PQ compression theory, and the two-phase search with reranking.

[options="header",cols="1,1,3"]
|===
|Parameter |Default |Description

|`onDisk`
|`false`
|Store the graph in a memory-mapped file instead of on the Java heap. This is what lets an index exceed available RAM: the OS pages the graph in and out, so heap stays flat and the cost moves to page cache and query latency. In-memory mode is faster per query but its graph is heap-resident, with the GC pressure that implies at scale.

|`indexDirectory`
|`null`
|Directory for index files. Required if `onDisk=true`.

|`vectorStorage`
|`INLINE`
|How the graph stores its own copy of each vector. `INLINE` keeps full precision (`dimension * 4` bytes per node). `NVQ` stores 8-bit quantized vectors (`4 + dimension + 28 * nvqSubvectors` bytes per node), which is about 3x smaller, and is the only setting that makes the graph file *smaller*. Reranking is exact under both, but reads from different places: an inline graph carrying fused codes reranks from its own mapping, while an NVQ graph has no full-precision copy and reads the GigaMap. With `approximateScoring=NONE` traversal reads the quantized vectors and so finds slightly different candidates; with `FUSED_PQ` the codes drive traversal and candidate selection is unchanged.

|`approximateScoring`
|`NONE`
|How traversal scores candidates. `NONE` scores from whatever the storage mode holds. `FUSED_PQ` writes Product Quantization codes into every node, which speeds up traversal of a large on-disk index at the cost of a *larger* graph file. `PQ_IN_MEMORY` buys the same approximate traversal without touching the graph, keeping the codes in heap - `pqSubspaces` bytes per ordinal, resident, against `pqSubspaces * maxDegree` bytes per node on disk. An on-disk index persists them in a `.pqv` sidecar read back on load; an *in-memory* index has no persist and therefore no sidecar, building them during optimization instead. It is also the only *PQ-based* mode available to an *in-memory* index - `NONE` remains the default there - and it requires `optimizationIntervalMs > 0`: the switch from exact to compressed scoring is a rebuild, and optimization is where it happens. A scheduled optimization is necessary but not sufficient: the background manager skips one until `minChangesBetweenOptimizations` changes have accumulated, and that defaults to 1000. An index that settles between the 256 vectors PQ training needs and that threshold stays on exact scoring until something calls `optimize()` explicitly, and `build()` warns when the two are configured that way.

|`nvqSubvectors`
|`0`
|Number of NVQ subvectors (0 = auto: 1). Each subvector adds a fixed 28 bytes per node on top of the one byte per dimension, so the default is almost always right. Not the same parameter as `pqSubspaces`, whose auto value would make an NVQ block larger than the vector it replaces. Only applies when `vectorStorage=NVQ`.

|`enablePqCompression`
|`false`
|*Deprecated*, use `approximateScoring` instead. A literal delegate: `true` means `FUSED_PQ`, `false` means `NONE`.

|`pqSubspaces`
|`0`
|Number of PQ subspaces (0 = auto: dimension/4). Under `FUSED_PQ` this costs `pqSubspaces * maxDegree` bytes per node on disk, so prefer a smaller value than classic PQ guidance suggests; under `PQ_IN_MEMORY` it is `pqSubspaces` bytes per ordinal in heap. Only applies when `approximateScoring` is one of those two.

|`parallelOnDiskWrite`
|`false`
|Use parallel direct buffers and multiple worker threads for on-disk index writing. Speeds up persistence for large indices but uses more resources. Only applies when `onDisk=true`.
|===

=== Example

[source, java]
----
VectorIndexConfiguration config = VectorIndexConfiguration.builder()
    .dimension(768)
    .similarityFunction(VectorSimilarityFunction.COSINE)
    .onDisk(true)
    .indexDirectory(Path.of("/data/vectors"))
    .approximateScoring(ApproximateScoring.FUSED_PQ)
    .pqSubspaces(48)  // Must divide dimension evenly
    .build();
----

== Eventual Indexing

Enable eventual indexing to defer expensive HNSW graph mutations to a background thread, reducing mutation latency at the cost of eventual search consistency.

[options="header",cols="1,1,3"]
|===
|Parameter |Default |Description

|`eventualIndexing`
|`false`
|Defer HNSW graph mutations (add, update, remove) to a background thread. The vector store is updated synchronously, but graph construction happens asynchronously. Search results may not immediately reflect the most recent mutations.
|===

When enabled:

* The vector store is always updated synchronously (no data loss).
* HNSW graph mutations are queued and applied by a single background worker thread.
* The queue is automatically drained before `optimize()`, `persistToDisk()`, and `close()`.

=== Example

[source, java]
----
VectorIndexConfiguration config = VectorIndexConfiguration.builder()
    .dimension(768)
    .similarityFunction(VectorSimilarityFunction.COSINE)
    .eventualIndexing(true)
    .build();
----

== Parallel On-Disk Writes

When on-disk storage is enabled, persistence can optionally use parallel direct buffers and multiple worker threads (one per available processor) to write the index concurrently. This can significantly speed up persistence for large indices. See xref:indexing/jvector/advanced.adoc#_parallel_on_disk_writes[Parallel On-Disk Writes] in the advanced section for more details.

This is disabled by default, as sequential single-threaded writing is preferred in resource-constrained environments or for smaller indices.

=== Example

[source, java]
----
VectorIndexConfiguration config = VectorIndexConfiguration.builder()
    .dimension(768)
    .similarityFunction(VectorSimilarityFunction.COSINE)
    .onDisk(true)
    .indexDirectory(Path.of("/data/vectors"))
    .parallelOnDiskWrite(true)
    .build();
----

== Background Persistence

Enable automatic asynchronous persistence to avoid blocking operations during writes.
Setting `persistenceIntervalMs` to a value greater than 0 enables background persistence. See xref:indexing/jvector/advanced.adoc#_production_configuration[Production Configuration] for a combined example with background persistence and optimization.

[options="header",cols="1,1,3"]
|===
|Parameter |Default |Description

|`persistenceIntervalMs`
|`0`
|Check interval in milliseconds. A value > 0 enables background persistence, 0 disables it.

|`minChangesBetweenPersists`
|`100`
|Debounce threshold: the background thread persists only once this many changes have accumulated. Lower values keep the on-disk graph closer to the live state, at the cost of more write amplification; higher values mean a crash discards more work, which the load-time rebuild then has to redo. `0` or `1` persists on every interval.

|`persistOnShutdown`
|`true`
|Persist pending changes on `close()` when `onDisk=true`. Applies whether or not background persistence is enabled.

|`shutdownPersistTimeoutMillis`
|`30000`
|How long `close()` waits for the final drain, optimize and persist before interrupting it and continuing. An aborted persist never loses data or leaves a torn file - on-disk indices write atomically and self-heal from the store - it only degrades to a rebuild on the next boot. In incremental on-disk mode the shutdown persist returns immediately, so in practice this bounds a first-time (non-incremental) persist or an unexpectedly slow drain.
|===

=== Example

[source, java]
----
VectorIndexConfiguration config = VectorIndexConfiguration.builder()
    .dimension(768)
    .similarityFunction(VectorSimilarityFunction.COSINE)
    .onDisk(true)
    .indexDirectory(Path.of("/data/vectors"))
    .persistenceIntervalMs(30_000)       // Enable, check every 30 seconds
    .minChangesBetweenPersists(100)      // Only persist if >= 100 changes
    .persistOnShutdown(true)             // Persist on close()
    .build();
----

== Background Optimization

Enable periodic graph optimization to maintain query performance as the index grows.
Setting `optimizationIntervalMs` to a value greater than 0 enables background optimization. See xref:indexing/jvector/advanced.adoc#_manual_optimization_and_persistence[Manual Optimization and Persistence] for manual control.

[options="header",cols="1,1,3"]
|===
|Parameter |Default |Description

|`optimizationIntervalMs`
|`0`
|Check interval in milliseconds. A value > 0 enables background optimization, 0 disables it.

|`minChangesBetweenOptimizations`
|`1000`
|Debounce threshold for background optimization. Should be higher than `minChangesBetweenPersists`, since a cleanup is the more expensive of the two. `0` or `1` optimizes on every interval.

|`optimizeOnShutdown`
|`false`
|Run a cleanup on pending changes during `close()`. Disabled by default because it blocks shutdown; leaving it off trades a slower first query after restart for a faster exit.
|===

=== Example

[source, java]
----
VectorIndexConfiguration config = VectorIndexConfiguration.builder()
    .dimension(768)
    .similarityFunction(VectorSimilarityFunction.COSINE)
    .onDisk(true)
    .indexDirectory(Path.of("/data/vectors"))
    .optimizationIntervalMs(60_000)       // Enable, check every 60 seconds
    .minChangesBetweenOptimizations(1000) // Only optimize if >= 1000 changes
    .optimizeOnShutdown(false)            // Skip for faster shutdown
    .build();
----
